## Why v2.0 exists (the through-line from v1)

v1's headline: no middleware arm cleared the native noise floor on a **non-caching,
request-metered rail** (ollama-cloud), on a **small** task. v1's two biggest caveats —
stated by us *and* conceded by the maintainers — were exactly the conditions v2 changes:

1. **"The no-cache rail understates the products."** Both maintainers said their tools
   **net ahead on cache-priced providers** (lean-ctx: "especially on cache-priced
   providers … it nets ahead"; headroom: cache-stabilization suite was structurally
   invisible on our rail). v2 moves to the **cache-priced Anthropic rail (opus/sonnet/
   haiku)** — the rail where they claim to win.
2. **"One small task can't resolve a ~7% effect against ~10× path variance."** v2 uses a
   **harder, real-world task**: find and correctly fix a planted one-token bug in git's
   `versioncmp` state table, oracle removed (GIT-BUG-003).

Plus: each product runs on its **latest version with the maintainer-recommended config**,
and we honor headroom's explicit 06-15 request (run headroom **without rtk**; they suspect
rtk induces loops). So v2 = *"we took the products to the rail where they claim to win,
with the configs they asked for, on a harder real task — does the verdict change?"*

## The task: GIT-BUG-003 (reuse the `../git/experiment` testbench)

Already built and partially run in `/home/boni/src/git/experiment/` — reuse its infra:
- **Bug:** one-token corruption in `versioncmp.c` `result_type[]` table, `S_N`/`d/d` cell
  `LEN→CMP` (version sort orders `9` > `10`). Data-not-logic, oracle removed (historyless
  single-commit repo, no `upstream` remote), camouflaged, no crash. See `experiment/BUG_SETUP.md`.
- **Invocation:** `/forge:fix-bug @engineering/bugs/GIT-BUG-003.md` → triage → [plan-fix →
  review-plan →] implement → review-code → approve → commit → finalize.
- **Decontamination + guards:** `stage-context.sh` strips `.git`/`experiment/`/artifacts and
  fails the build if `versioncmp|result_type|strverscmp|S_N|LEN` leaks into brief/KB/store.
- **Adjudication:** `experiment/JUDGE.md` — objective oracle (reproducer prints ascending
  order) + root-cause test (fixed the table, not a symptom mask) + suite green. Run OUTSIDE
  the harness, re-verified independently.
- **Evidence:** `run.sh` captures `transcripts/`, `final.diff`, `final-tree/versioncmp.c`,
  build/repro/test logs, `run-meta.json` per run into `experiment/runs/<arm>/<ts>/`.

**DECIDED (2026-06-15): cost is the headline; capability is a gate.** The primary verdict is
**per-arm cost on the cache-priced rail** (cache-aware token buckets + USD per run vs pristine
×3). A run only counts toward the cost comparison if it **passes the JUDGE gate** (fix landed
+ root cause + suite green) — a failed/looped/symptom-masked run is reported separately, not
priced (mirrors v1's engage-check/void discipline). So v2 *is* a cost benchmark, now on the
rail where the products claim to win, with capability as the validity gate rather than the story.

## Model wiring (the rail)

**DECIDED:** per-phase mix = **head (review/approve) = opus · sub (plan/implement/commit) =
sonnet · low (finalize) = haiku.** Held identical across every arm; the **arm** is the only
IV. (The existing capability experiment used opus/opus/haiku and fable/fable/haiku; v2's
product study fixes this opus/sonnet/haiku mix instead.)

Cache-priced rail means the token meter must split **cache-write vs cache-read vs fresh
input** and report **USD** (v1's a0c run already proved the Anthropic harness path: ~92%
cache reads, $1.82 actual). Per-arm cost comparison is the cache-aware version of v1's metric.

## Metrics

- **Primary (cost, the headline):** per-arm **USD per passing run** + cache-aware token
  buckets (cache-read · cache-write · fresh-input · output), per phase and total, vs pristine
  ×3. Only **gate-passing** runs are priced.
- **Gate (capability validity):** fix landed (canonical/equivalent-correct per JUDGE) · root
  cause found · verified (rebuilt git sorts ascending, suite green). Pass/fail per run; fails
  reported separately, excluded from the cost comparison.
- **Secondary (process):** turns, tool calls/errors, **loop incidence** (headroom-no-rtk
  observation), review-iteration count, path A/B.
- **Failure modes:** wrong file, symptom mask, gave up, looped, false "fixed".

## Update 2026-06-15 — lean-ctx arm: maintainer PR + the moving-target problem

**yvgude reply** (lean-ctx#361 comment 4706844845): in for v2/R2; endorses the
GIT-BUG-003 capability framing (on a fix task cost = turns × rate, so what matters is
whether a context layer helps *localize* the bug and whether a blind compressor ever
compresses the bug-relevant cell *away*). Verbatim captured in notes/09.

**Decisions:**
- **lean-ctx arm = accept the maintainer's integration PR** (the lean-ctx analogue of
  headroom #823). It fixes the exact unfaithfulness we hit building by hand: R1 logged
  **102 native bash / 0 ctx_shell** — the compressor never saw build/test/make output (the
  heaviest payload on a fix task), because the pi extension's shell tool wasn't routed.
  PR contents: pi shell-routing fix (lossless for signal — compiler/test/panic kept
  verbatim) + faithful config (`rules_injection=off`, minimal tool profile, `structure_first`
  cold-read bias that always full-reads diagnostic/edit-fail/small/task-named files) + meter
  net-of-injection. Build-by-inference REJECTED (would reproduce the 0-ctx_shell trap).
- **Warm-session/long-lived arm = DEFERRED.** v2 stays phase-isolated (matches the
  testbench as built). Logged as future work ("two arms, two truths" — his request #2).
- **Both rails = already satisfied.** v1 = non-caching ollama-cloud; v2 = cache-priced
  Anthropic. The two studies already tell his two-sided story (his request #1).

**MOVING-TARGET CAVEAT (must be in the writeup, and a guardrail on the arm):**
lean-ctx shipped **8 npm releases in 9 days** during the benchmark window
(3.7.3 2026-06-04 → 3.8.5 2026-06-14; 92 versions total), each burst landing right after
one of our filings (#361 06-06 → 3.7.4/3.7.5; right-of-reply + v2 prep 06-12→14 → 3.8.0–3.8.5).
This is a product being tuned to the test in real time. It is the strongest form of "the
benchmark improves the product" — and simultaneously a real **external-validity risk**
(are we measuring what public users run, or a benchmark-special build?). Guardrails:
1. **Pin the arm to a PUBLIC released version** (npm tag, date-stamped), never a private
   branch. The maintainer PR must land in a public release to count as THE result; until
   then it's a clearly-labeled "vendor-recommended faithful variant," not the headline.
2. **Separate genuine product fix from benchmark config.** The shell-routing fix is a real
   extension bug fix (verify it's in the public pi-lean-ctx + lossless). `rules_injection=off`
   / minimal profile / `structure_first` are user-settable config knobs — fair to use as the
   documented faithful config, disclosed as vendor-recommended.
3. **Disclose the velocity with dates** — every benchmark-responsive release, so a reader
   sees the target moved during the study. Same treatment for headroom (0.24→merged #823).
4. **Date-stamp + freeze the v2 arm versions** the way v1 froze forge-cli; "latest" drifts
   under this cadence (it moved 3.8.0→3.8.5 in the 3 days we've been prepping).
